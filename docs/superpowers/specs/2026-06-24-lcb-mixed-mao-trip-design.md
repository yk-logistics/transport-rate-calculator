# LCB ลูกผสม เหมา/เที่ยว — โหมด `lcb_mixed` (per-day mode)

วันที่: 2026-06-24
สถานะ: design (รออนุมัติจากโอ)

## ปัญหา

คนขับ LCB บางคนในรอบเงินเดือนเดียวกัน วิ่ง **บางวันแบบเหมา บางวันแบบเที่ยว** เกิดจาก 2 สถานการณ์จริง:

- **เคส A — เปลี่ยนระบบกลางรอบ:** คนตั้งใจเปลี่ยนเหมา↔เที่ยว เป็นช่วงยาว (เช่น เที่ยวต้นรอบ → เหมาท้ายรอบ)
- **เคส B — ย้ายรถกระทันหัน:** ปกติเหมาอยู่แล้ว แต่บางวันถูกย้ายไปขึ้นรถคันอื่น วิ่งไม่กี่เที่ยว เลยจ่ายเป็นเที่ยวเฉพาะวันนั้น

ระบบปัจจุบันตั้ง `pay_mode` ได้ค่าเดียวต่อคนต่อรอบ คิดผสมรายวันไม่ได้ ตัวอย่างรอบ 16/5–15/6: **พชร** (เหมา~16 / เที่ยว~18 วัน) และ **สุรเดช** (เหมา~9 / เที่ยว~29 วัน)

## เป้าหมาย / Success criteria

1. เพิ่มโหมด `lcb_mixed` ที่ engine คิดเงิน **รายวัน**: วันเหมาคิดแบบเหมา วันเที่ยวคิดแบบเที่ยว รวมเป็น **1 PayRunItem ต่อคน**
2. ครอบคลุมทั้งเคส A และ B ด้วย logic เดียว (ไม่สนรูปแบบการสลับ เพราะคิดทุกวัน)
3. สลิป 1 ใบ แสดง **แยกส่วนเหมา / เที่ยว** ให้อ่านออกว่าได้จากแต่ละระบบเท่าไหร่
4. ออกแบบ generic — ใช้กับคนไหนก็ได้ในอนาคต ไม่ผูกกับพชร/สุรเดช
5. **ไม่กระทบการคำนวณของอีก 16 คน** ในรอบ (โหมดเดิมทำงานเหมือนเดิมทุกบาท)
6. ตรวจย้อนกลับได้: มี preview read-only ก่อนเขียน + เทียบยอดก่อน finalize

## กฎโดเมน (โอยืนยัน 2026-06-24)

- **กฎตัดสินวันเหมา/เที่ยว — ใช้ ratio เป็นหลัก:** ต่อ DailyJob 1 วัน คำนวณ `ratio = trip_fee_driver / revenue_customer`
  - `revenue > 0` และ `ratio ≈ 0.60` (±0.05) → **วันเหมา** (เพราะค่าเที่ยวที่จ่าย = 60% ของค่าขนส่ง = สูตรเหมา)
  - `revenue > 0` และ ratio ต่ำ (สังเกตจริง ~7–8%) → **วันเที่ยว**
  - `revenue = 0` (วันว่าง/ไม่มีงาน) → กำกวม ไม่มีเงินอยู่แล้ว → **ไม่นับเป็นวันทำงานทั้งสองระบบ**; ถ้ามีความกำกวมที่กระทบเงิน ระบบ **flag ให้ถามโอ** ไม่เดาเอง
  - สีฟ้าในชีทพี่ตาลเป็นสัญญาณ **รอง** (พี่ตาลอาจลืมใส่สี) — ratio แม่นกว่า ตรวจพบ ratio=60.0% เป๊ะตรงกับสีฟ้าทุกวันที่ทำงานจริง
- **ฐาน+ดูแล (LCB 9,240 + 3,000):** คนลูกผสมได้ฐาน **เฉพาะสัดส่วนวันเที่ยว** (วันเหมาไม่มีฐานตามกติกาเหมา) — prorate ด้วย (วันเที่ยว ÷ วันในรอบ) แทนการ prorate ด้วยทั้งรอบ
- **น้ำมัน:** วันเหมาคนขับออกเอง → หักเฉพาะน้ำมันของวันเหมา (วันเที่ยวบริษัทออก ไม่หัก)
- **พิเศษ 100฿/เที่ยว (LCB):** ใช้เฉพาะวันเที่ยว (เป็นกติกาฝั่งเที่ยว)
- **SS / ภาษี / เบิก / ประกัน(deposit) / อุบัติเหตุ:** คิด **ครั้งเดียวรวมทั้งคน** เหมือนคนปกติ (ไม่แยกตามวัน) — เพราะเป็น 1 PayRunItem

## สถาปัตยกรรม

### หลักการ
สร้าง pay_mode ใหม่ `lcb_mixed`. ใน `calc_one_employee` เพิ่ม branch สำหรับโหมดนี้ที่:
1. ดึง DailyJob ทุกวันในรอบ → จำแนกแต่ละวันเป็น `mao_day` หรือ `trip_day` ด้วยกฎ ratio
2. **ฝั่งเหมา:** `fuel_share_income = Σ(revenue ของ mao_days) × share_rate(0.60)`; `fuel_cost_self = Σ(น้ำมันของ mao_days)`
3. **ฝั่งเที่ยว:** `trip_fee_total = Σ(trip_fee ของ trip_days)`; `other_income += (จำนวน trip_days ที่มีงาน?) ...` พิเศษ 100×เที่ยว เฉพาะ trip_days
4. **ฐาน:** prorate ด้วยสัดส่วนวันเที่ยว: `base_earned = base × (trip_days / days_in_month)` (ทำนองเดียวกับ care)
5. รวมทุกฝั่งเข้า field เดิมของ PayrollCalc (fuel_share_income, trip_fee_total, fuel_cost_self, base_salary_earned, care_allowance_earned, other_income) → `gross_total`/`net_pay` คิดต่อด้วย logic เดิม
6. หักทั่วไป (SS/ภาษี/เบิก/ฯลฯ) ใช้ path เดิมไม่เปลี่ยน

### ทำไมเลือกแบบนี้ (1 บรรทัด ไม่ใช่ 2 บรรทัด)
- ไม่ต้องแตะ `compute_pay_run` roster (ยังคง 1 emp = 1 item) → ไม่กระทบ finalize / override / สลิป ที่ assume 1:1
- SS/ภาษี/เบิก คิดครั้งเดียว → ไม่เสี่ยงหักซ้ำ/หักขาดจากการกระจาย 2 บรรทัด
- ฟิลด์ผลลัพธ์มีอยู่แล้ว (fuel_share_income vs trip_fee_total) → สลิปแยกส่วนได้โดยไม่เพิ่ม schema

### หน่วยงาน (units) ที่แตะ
- **`_classify_lcb_days(session, emp_id, start, end, site)`** (ใหม่) — คืน `(mao_days: list[DailyJob], trip_days: list[DailyJob], ambiguous: list[DailyJob])`. ทดสอบแยกได้ด้วย daily rows สังเคราะห์.
- **`_sum_fuel_cost_for_days(...)`** — น้ำมันเฉพาะชุดวันที่กำหนด (เหมา). อาจ reuse `_sum_fuel_cost` โดยส่งช่วงวัน/เซ็ตวัน.
- **branch `lcb_mixed` ใน `calc_one_employee`** — ประกอบผลจาก helper.
- **note string** — สรุป "เหมา Nวัน rev×60% − น้ำมัน | เที่ยว Mวัน ค่าเที่ยว" เพื่อ trace ย้อนกลับ.
- **สลิป template** (`templates/`) — section ลูกผสมแสดง 2 หัวข้อย่อย (เหมา/เที่ยว) เมื่อ mode == lcb_mixed.

### สิ่งที่ "ไม่มี" สัญญาณ per-day mode ใน DB
ปัจจุบัน DailyJob ไม่มีคอลัมน์ mode ต่อวัน — **ไม่เพิ่มคอลัมน์** เพราะ ratio คำนวณจาก revenue/trip_fee ที่มีอยู่แล้วได้ทันที (YAGNI). ถ้าอนาคตเจอวันกำกวมเยอะค่อยพิจารณาเพิ่ม override ต่อวัน.

## Data flow

```
DailyJob (per day, revenue+trip_fee)
   │  _classify_lcb_days (ratio 60%)
   ├── mao_days  → Σrevenue×60%  +  Σfuel(mao days) as cost_self
   ├── trip_days → Σtrip_fee  +  พิเศษ 100×เที่ยว  +  ฐาน×(trip_days/period)
   └── ambiguous (rev=0) → ข้าม (flag ถ้ากระทบเงิน)
            │
            ▼
   PayrollCalc (1 ชุด) → gross_total → หัก SS/ภาษี/เบิก (path เดิม) → net_pay
            │
            ▼
   PayRunItem (1 แถว) → สลิปแสดงแยกส่วนเหมา/เที่ยว
```

## Error / edge handling

- **ratio กำกวม** (revenue>0 แต่ ratio อยู่กลางๆ ไม่ใช่ ~60 ไม่ใช่ ~7): ระบบ **ไม่เดา** → ใส่ในรายการ ambiguous + note เตือน "ต้องให้โอตัดสิน" และ (ชั่วคราว) ปฏิบัติเป็นวันเที่ยว (อนุรักษ์นิยม: ไม่หักน้ำมันโดยพลการ) จนกว่าโอยืนยัน. รายงาน preflight จะลิสต์วันพวกนี้.
- **ไม่มี DailyJob เลย** ในรอบ: net = ฐานตามสัดส่วน 0 → behave เหมือนคนไม่มีงาน (เดิม).
- **fuel มากกว่ารายได้** (วันเหมาน้ำมันแพง): net ติดลบได้ — ใช้กติกาเดียวกับ mao ปกติ (โอเคยรับ negative ได้).
- **เปลี่ยนคนจาก lcb_trip/lcb_mao เดิม → lcb_mixed:** แค่เปลี่ยน pay_mode + recompute; ไม่ย้ายข้อมูล.

## Testing

- **Unit `_classify_lcb_days`:** daily rows สังเคราะห์ — วัน ratio 0.60 → mao, 0.07 → trip, rev=0 → ambiguous, ratio 0.30 → ambiguous.
- **calc `lcb_mixed` ด้วยข้อมูลจริงพชร/สุรเดช:** เทียบยอดเหมา-ส่วน + เที่ยว-ส่วน กับการคำนวณมือ (สเปรดชีต) ของโอ.
- **Regression:** คน 16 คนเดิมในรอบ — รัน compute_pay_run ก่อน/หลังเพิ่มโหมด net ต้องเท่าเดิมทุกบาท (โหมดใหม่ไม่แตะ path เดิม).
- **Preview read-only ก่อนเขียน:** สคริปต์โชว์ per-day classification + ยอด 2 ฝั่ง ให้โอตรวจก่อน recompute จริง.

## ขอบเขตที่ "ไม่ทำ" (YAGNI)

- ไม่เพิ่มคอลัมน์ mode ต่อวันใน DailyJob (ratio พอแล้ว).
- ไม่ทำ UI ตั้ง per-day mode (ใช้ ratio อัตโนมัติ + flag กำกวม).
- ไม่แตะโหมดไซต์อื่น (BIGC/AYU) — เฉพาะ LCB.
- ไม่ทำ 2-บรรทัด-แยก (ตัดสินใช้ 1 บรรทัด).

## แผนส่งมอบ

1. โหมด + helper + unit test (ไม่แตะ path เดิม) → regression 16 คน net เท่าเดิม.
2. Preview read-only พชร/สุรเดช → โอตรวจยอดเทียบมือ.
3. เปิดใช้กับพชร/สุรเดช (และสุภาพถ้าจำเป็น) → recompute → โอตรวจในแอป.
4. สลิปแสดงแยกส่วน.
5. finalize เมื่อโอ OK.
