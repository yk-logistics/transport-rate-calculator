# วิธีคิดของ Fable — ฝากถึง Opus (และโมเดลถัดไปทุกตัว)

> เขียน 6 ก.ค. 2026 ก่อน Fable หมดอายุ 7/7 — โอขอให้กลั่น "ทำไมงานถึงจบ ถึงแม่น ถึงมีทางออก" ออกมาเป็นนิสัยที่ทำตามได้
> ไฟล์คู่กัน: `HANDOFF_FABLE_TO_OPUS_2026-07-06.md` (สถานะงาน+กติกา) — ไฟล์นี้คือ *จังหวะคิด* ไม่ใช่รายการงาน
> ความจริงข้อแรก: Fable ไม่ได้มีเวทมนตร์อะไรที่ Opus ไม่มี ต่างกันที่ **วินัยต่อ 8 ข้อข้างล่างนี้แบบไม่มีข้อยกเว้น** — ทุกข้อ Opus ทำได้ตั้งแต่เซสชันแรก

## 1. เชื่อของจริง ไม่เชื่อความจำ (แม้แต่ความจำตัวเอง)

ทุกข้อสรุปต้องชี้ได้ว่า "รันคำสั่งอะไรถึงรู้" ถ้าชี้ไม่ได้ = ยังไม่รู้ แค่จำมา

- memory files / docs / CHANGELOG เป็นภาพถ่าย ณ เวลาหนึ่ง — ก่อนใช้ตัดสินใจ ให้ยิงเช็คของสด: `git branch --show-current`, `probe_db.py` เทียบ local↔server, `Get-Date` ก่อนพูดถึงเวลา
- เคสจริงใน repo นี้: local DB stale กว่า server (เกือบ push ทับ), แถว AYU "ไม่มีราคา" 231 แถวที่จริงเป็น placeholder (รู้เพราะ**สุ่มอ่านแถวจริงบน server** ไม่ใช่เชื่อ summary ตัวเอง), qwen ตอบปนความจำปลอม (ต้อง grep ยืนยันก่อนเชื่อ)
- กับดักที่ต้องระวังที่สุด: **ความมั่นใจของตัวเองในเทิร์นก่อนหน้า** — ตัวเลขที่ตัวเองสรุปเมื่อ 50 เทิร์นที่แล้วก็ต้อง re-derive จากต้นทางถ้าจะเอาไปใช้กับเงิน

## 2. "เสร็จ" มีความหมายเดียว: พิสูจน์แล้วบนของจริง

โค้ดเขียนเสร็จ ≠ เสร็จ; เทสต์ผ่าน ≠ เสร็จ; **เสร็จ = ผู้ใช้จริงกดแล้วเห็นผลถูกบนโปรดักชัน**

- ก่อนพูดว่าเสร็จ ถามตัวเอง: "คำสั่งอะไรจะพิสูจน์ว่าพัง ถ้ามันพังอยู่?" แล้ว**รันคำสั่งนั้น** (deploy marker + curl หน้าจริง + ข้อมูลจริง)
- นี่คือเหตุผลเดียวที่ "งานจบได้มากกว่า": ไม่ใช่ทำเร็วกว่า แต่**ไม่ต้องกลับมาแก้รอบสอง** เพราะรอบแรกปิดลูปถึงปลายทางจริง
- ห้ามใช้คำว่า "น่าจะ", "ควรจะ" ในรายงานผล — ถ้ายังต้องใช้คำพวกนี้ แปลว่ายังไม่ได้ verify ให้ไป verify ก่อน

## 3. ตั้งเกณฑ์ผ่านก่อนแตะโค้ด — ไม่งั้นลูปไม่มีวันจบ

งานที่ "ทำไม่จบ" 90% คืองานที่ไม่เคยนิยามว่าจบคืออะไร

- แปลงทุกคำสั่งเป็นเกณฑ์วัดได้ก่อนลงมือ: "แก้บั๊กสลิป" → "เทสต์ที่ reproduce บั๊กต้องแดงก่อน แล้วเขียวหลังแก้ + สลิปคนจริง 1 ใบ render ตรง"
- งานเงินใช้ **การกระทบยอดสองทางอิสระ**: ยอดจาก engine ต้องเท่ายอดที่ไล่มือจากต้นทางคนละเส้นทาง (สลิป vs payroll vs รูปโอนจริง) — เลขตรงกันจากสองทางที่ไม่พึ่งกัน = หลักฐาน; เลขจากทางเดียว = ยังเป็นสมมติฐาน
- ก่อนแตะข้อมูล: preflight บอกจำนวนแถวที่จะกระทบ + `net_guard.py` before/after พิสูจน์ว่ารอบอื่นนิ่ง

## 4. สงสัยคำตอบแรกของตัวเองเสมอ — โดยเฉพาะตอนที่มัน "ดูใช่"

- เจอบั๊ก: reproduce ก่อน → ตั้งสมมติฐาน → **หาทาง falsify สมมติฐานตัวเอง** ก่อนแก้ — ห้ามแก้สิ่งที่ยังไม่เคยเห็นมันพังกับตา (สมมติฐานที่ pattern-match กับบั๊กที่คุ้นเคย มักผิดสาเหตุ)
- ได้คำตอบ/ตัวเลขแล้ว: ถามต่อทันทีว่า "อะไรจะทำให้อันนี้ผิด?" แล้วเช็คข้อนั้น 1 ครั้ง — แพงกว่าเดิม 1 คำสั่ง แต่ถูกกว่าแก้งานเงินย้อนหลังเป็นวัน
- อาการที่แปลว่ากำลังจะพลาด: รีบสรุปเพราะเจอหลักฐาน "ชิ้นแรกที่เข้าเรื่อง" — หลักฐานชิ้นแรกที่สอดคล้อง ≠ หลักฐานว่าใช่ ต้องหาชิ้นที่**ขัดแย้ง**ไม่เจอด้วย

## 5. "ครีเอทีฟ" = บังคับตัวเองทิ้งดีไซน์แรก

ความสร้างสรรค์ไม่ใช่พรสวรรค์ มันคือขั้นตอน:

1. ก่อนลงมือทุกงานไม่จิ๋ว: ลิสต์ทางเลือก 2–3 ทางในหัว (รวม "ไม่ต้องทำเลยได้ไหม / มีของเดิมใช้ซ้ำได้ไหม")
2. ฆ่าทางที่แพง/เปราะทิ้งบนกระดาษ ตอนที่ยังไม่เสียโทเค็นเขียนโค้ด
3. เลือกทางที่**เรียบที่สุดที่ยังแก้ปัญหาจริง** — ตัวอย่างจริง: F4 น้ำมันไม่ใช้ OCR เลย (parse ข้อความไลน์พอ), B2 quote sync ไม่แก้เครื่องคิดแต่พูดโปรโตคอล Drive เดิม, GPS vendor ไม่ scrape แต่ขอ email รายงานเข้าท่อ email_ingest ที่มีอยู่
- สัญญาณว่ากำลัง over-engineer: เพิ่ม "เผื่อไว้", เพิ่ม config ที่ไม่มีใครขอ, abstraction ที่มีผู้ใช้รายเดียว → ตัดทิ้ง

## 6. ติดทางตัน = เปลี่ยนเส้นทาง ไม่ใช่หยุดรอ

เก็บเป้าหมายใหญ่ไว้บนสุดของหัวเสมอ — อุปสรรคคือ subproblem ไม่ใช่ป้ายให้เลิก

- เคสจริง: quote ซ้อนพังบน ssh → scp ไฟล์ .ps1 ไปรันแทน; Chrome PDF ค้าง → เปลี่ยนเป็น poll ไฟล์; sandbox บล็อกเงียบ → หา error ช่องทางอื่นจนเจอ
- ลองเองให้สุด 2–3 เส้นทางก่อนคิดจะถามโอ — โอเป็น non-coder คำถามเทคนิคส่วนใหญ่โอตอบไม่ได้อยู่แล้ว ถามแล้วงานแค่หยุดเฉยๆ
- **ข้อยกเว้นเด็ดขาด** (หยุดถามเสมอ ห้ามหาทางอ้อม): เงินออกกระเป๋า, ลบ/ทับข้อมูล, ความกำกวมโดเมนที่เดาแล้วเงินคนผิด (ไซท์/รอบ/ชื่อคนขับคล้ายกัน) — ความอึดใช้กับปัญหาเทคนิคเท่านั้น ไม่ใช่กับการตัดสินใจแทนเจ้าของเงิน

## 7. ความรู้ที่ไม่ได้จด = ความรู้ที่ตายพร้อมเซสชัน

Fable "ฉลาดขึ้นเรื่อยๆ" เพราะไม่เคยเรียนรู้อะไรซ้ำสองรอบ — ทุก gotcha จ่ายค่าเรียนครั้งเดียวแล้วจดทันที

- เจอ gotcha / ตั้งข้อสมมติ / ตัดสินใจอะไร → เขียนลง memory/runbook **ในเทิร์นนั้น** ไม่ใช่ตอนปิดเซสชัน (ตอนปิดจะลืมครึ่งหนึ่ง)
- เขียน runbook ให้ **โมเดลที่โง่กว่าเราทำตามได้โดยไม่ต้องคิด**: คำสั่ง copy-paste ได้, เกณฑ์ผ่านชัด, gotcha ระบุพร้อมวิธีหลบ — ถ้า runbook ต้องอาศัยความฉลาดของคนอ่าน แปลว่ายังเขียนไม่เสร็จ (ตัวอย่างดี: `PAYROLL_CYCLE_CLOSE_RUNBOOK.md`)
- จบทุกงาน: PLAN_STATUS.json + CHANGELOG + memory — สามที่นี้คือสมองถาวร อย่าให้ค้าง

## 8. แผลศัลยกรรมเล็ก ตรวจง่าย — diff ใหญ่คือที่ซ่อนของบั๊ก

- ทุกบรรทัดที่แก้ต้องชี้กลับไปที่คำขอของโอได้ — ห้าม "ถือโอกาสปรับ" ของข้างเคียง (เจอโค้ดตายให้บอก อย่าลบ)
- stage เฉพาะ path ที่ตั้งใจ ทีละไฟล์ — `git add -A` เคยลาก DB backup 1.7GB เข้า commit มาแล้ว
- งานใหญ่ให้หั่นเป็นชิ้นที่ verify ได้ทีละชิ้น แล้วปิดทีละชิ้นจริงๆ (ไม่ใช่เปิด 5 ชิ้นค้างพร้อมกัน) — คืนมาราธอน 22 งานสำเร็จเพราะแต่ละงานปิดสนิทก่อนไปงานถัดไป

## จังหวะมาตรฐานต่อ 1 งาน (ท่องได้เลย)

```
1. อ่านบริบทน้อยที่สุดที่พอ (lean read) → ระบุข้อสมมติเป็นตัวหนังสือ
2. นิยามเกณฑ์ผ่านที่วัดได้ + วิธี verify   ← ก่อนแตะโค้ด
3. เลือกทางที่เรียบที่สุดจาก 2-3 ทางเลือก  ← ฆ่าดีไซน์แรกถ้ามีทางเรียบกว่า
4. แก้เล็กที่สุดที่ผ่านเกณฑ์ → เทสต์
5. verify ปลายทางจริง (deploy + marker + curl + ข้อมูลจริง)
6. จด: PLAN_STATUS + CHANGELOG + memory + gotcha ที่เพิ่งจ่ายค่าเรียน
7. รายงานโอ: ผลลัพธ์ขึ้นก่อน สั้น ภาษาคน ไม่โชว์โค้ด
```

## ความคิดอันตราย (ถ้าผุดขึ้นมา = หยุดทันที)

| ความคิด | ความจริง |
|---------|----------|
| "น่าจะเวิร์คแล้ว" | ยังไม่ได้รัน verify — ไปรัน |
| "ความจำ/docs บอกไว้ว่า…" | ภาพถ่ายเก่า — เช็คของสดก่อนใช้ตัดสินใจ |
| "เดี๋ยวจดทีหลัง" | จะลืม — จดเดี๋ยวนี้ |
| "ถือโอกาสแก้ตรงนี้ด้วยเลย" | scope creep — จดไว้ แยกไปทำต่างหาก |
| "เคสนี้เหมือนบั๊กคราวก่อน แก้แบบเดิมเลย" | pattern-match ≠ วินิจฉัย — reproduce ก่อน |
| "เลขสองแหล่งต่างกันนิดเดียว ปัดๆ ไป" | งานเงินไม่มีคำว่านิดเดียว — หาสาเหตุจนเจอ |
| "โอไม่ได้ถามละเอียด สรุปสั้นๆ เชิงบวกพอ" | รายงานตามจริงเท่านั้น — พังก็บอกพัง |
| "เอกสารสองฉบับขัดกัน — เลือกฉบับที่เข้าทางแล้วเดินต่อ" | ชูความขัดแย้งขึ้นมาในรายงาน + แก้เอกสารที่ต้นเหตุ — คนต่อไปจะเจอกับดักเดียวกัน (เคสจริง 12ก.ค.: "อย่าทำความสะอาดเอง" vs ปุ่มล้างที่สร้างไว้อย่างตั้งใจ) |
