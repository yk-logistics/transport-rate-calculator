# สเปคฟีเจอร์: Job Booking → บอร์ดจัดรถ → ร่างเดลี่ (+ GPS เฟสถัดไป)

มติจาก grill-me กับโอ 2026-06-10 (เซสชัน "MVP Overall") — เอกสารนี้คือ source of truth ของฟีเจอร์ ห้ามออกแบบใหม่โดยไม่อ่าน

## บริบทธุรกิจ (ทำไมต้องมี)

- ลูกค้าแจ้งงานทาง **LINE เป็นหลัก** + ส่งใบงานทางเมล/ไลน์ · ล่วงหน้าตั้งแต่วันต่อวันถึงรายสัปดาห์ · **เปลี่ยน/เลื่อน/ลด/ยกเลิกบ่อย**
- ปัจจุบัน: **หัวหน้าลานจัดรถใน Notepad บนคอม** แล้วพิมพ์สรุปส่งไลน์กลุ่มคนขับ → ไม่มีบันทึกในระบบ, OP2 คีย์เดลี่จากศูนย์ทุกเช้า
- ระบบมี `dispatchplan/-line/-audit` + UI `/dispatch_planner` อยู่แล้ว (draft/submit, สร้างข้อความ LINE, audit) — **เริ่มจากรถ ไม่ได้เริ่มจากงาน** ส่วนที่ขาดคือ booking ชั้นหน้า

## มติออกแบบ (ล็อกแล้ว)

1. **Booking = ออเดอร์ มีช่อง "จำนวนคัน"** (ไม่ใช่ 1 ใบ = 1 คัน) — ฟิลด์ขั้นต่ำ: วันที่งาน, ลูกค้า, สถานที่รับ/ส่ง, ประเภทรถ, เวลา, จำนวนคัน, หมายเหตุ + สถานะ (`รอจัด / จัดบางส่วน / จัดครบ / เลื่อน / ยกเลิก`) + ประวัติการแก้ (รองรับเปลี่ยน/ลด/เลื่อน/ยกเลิกบ่อย)
2. **บอร์ดจัดรถ: จอคอมเป็นหลัก, จับคู่แบบ "แตะสองครั้ง"** (คลิกงาน → คลิกรถ) — ผู้ใช้คือหัวหน้าลาน (ชิน Notepad) ต้องเรียบง่ายสุด · ซ้าย = ออเดอร์ของวัน (การ์ดโชว์ "ขาดอีก N คัน") · ขวา = รถ+คนขับ (ว่าง/จัดแล้ว/ซ่อม/ลา) · **drag-drop = ของเสริมทีหลัง** (SortableJS CDN ได้ ไม่บังคับ)
3. **จัดครบแล้ว → สร้างข้อความสรุปส่งไลน์กลุ่มคนขับ** (reuse `line_message_cache` ของ dispatch planner เดิม)
4. **เช้าวันงาน ระบบสร้าง "แถวเดลี่ร่าง" อัตโนมัติ** จากผลจัดรถ (วันที่/รถ/คนขับ/ลูกค้า/เส้นทาง pre-filled) — OP2 เติมของจริง (เลขตู้, เวลา, น้ำมัน) แล้วยืนยัน · เก็บทั้ง "แผน" และ "จริง" เทียบกันได้ → **นี่คือเกณฑ์ผ่านหลักของฟีเจอร์**
5. **ตารางสถานที่กลาง (Location master)**: autocomplete + ปุ่มเพิ่มใหม่ในหน้าคีย์ (สถานที่มีทั้งเจ้าประจำและเพิ่มใหม่เรื่อยๆ) · มีช่อง lat/lng + รัศมี + dwell ขั้นต่ำ (เว้นว่างได้) — **ตารางเดียวกันนี้ = POI ของ GPS ในอนาคต**

## GPS (backlog หลัง MVP — รอสรุปเจ้า GPS)

- สถานะผู้ให้บริการ: เดิม **Mobile Innovation** กำลังต่อรองรั้งไว้ / ตัวเลือกใหม่ **Cartrack** — ยังไม่คุยเรื่อง API ทั้งคู่
- **การบ้านโอ (ทำได้ทันที):** ส่งคำถาม 5 ข้อให้ทั้งสองเจ้าตอบแข่งกัน เป็นเกณฑ์เลือกด้วย: ① API ตำแหน่งปัจจุบันทุกคัน ดึงถี่สุดเท่าไหร่ ② API ประวัติเส้นทาง ย้อนได้กี่วัน ③ ค่า API เพิ่มเท่าไหร่ (ต่อคัน/เดือน) ④ ขอ docs + ตัวอย่าง JSON ⑤ ย้ายเจ้าแล้วเอาประวัติออกมาได้ไหม
- **สถาปัตยกรรม: adapter ต่อเจ้า** — โครงข้อมูลภายใน (ตำแหน่ง, POI=Location master, timeline) เป็นของเรา เปลี่ยนเจ้า = เขียน adapter ใหม่ตัวเดียว → ไม่ต้องรอเจ้าสรุปก็ออกแบบฝั่งเราได้
- **เฟสตามลำดับ (มติ):**
  1. **เห็นรถ** — ตำแหน่งปัจจุบันทุกคัน รายการ+แผนที่ (วิ่ง/จอด/อยู่ลาน)
  2. **Timeline อัตโนมัติ** — GPS history × POI → ต่อคันต่อวัน: ออกลาน→ท่าเรือ/ลานตู้→ต้นทาง→ปลายทาง→กลับลาน เทียบแผนจัดรถ+เดลี่ (หัวใจของก้อนนี้)
  3. **เตือน** — ออกนอกเส้นทาง / ไปที่ที่ไม่มีในใบงาน / GPS เห็นวิ่งงานแต่เดลี่ไม่มีแถว (หัวหน้าลืมแจ้ง) · กฎ dwell: อยู่ในรัศมี POI ≥ X นาที (default 10, override รายสถานที่) กัน "แค่วิ่งผ่าน" · **เตือนในหน้าระบบก่อน** ยิง LINE ทีหลัง
