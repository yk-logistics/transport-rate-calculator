# ความปลอดภัยระบบ MVP — อธิบายให้โอ (ภาษาคน)

อัปเดต 2026-06-15 · เขียนตอบคำถามโอเรื่อง "ถ้าเครื่องพนักงานติดไวรัส / โดนดักข้อมูล จะมีช่องโหว่ไหม"

---

## สรุปสั้น

ระบบนี้ป้องกันได้ดีในระดับที่ควรเป็นสำหรับธุรกิจ — **แต่มีอยู่ 1 อย่างที่ไม่มีระบบไหนในโลกป้องกันได้** คือ ถ้าเครื่องของ user ติดไวรัสที่ดักแป้นพิมพ์ (keylogger) มันจะเห็นรหัสตอนพิมพ์ ก่อนที่ระบบเราจะได้เข้ารหัสด้วยซ้ำ อันนั้นต้องแก้ที่เครื่อง user (ลงแอนตี้ไวรัส) ไม่ใช่ที่ server

ที่เหลือ เราปิดช่องไว้หมดแล้ว — ดูตารางข้างล่าง

---

## ถ้าเครื่อง user ติดไวรัส ไวรัสทำอะไรได้ / ไม่ได้

| สิ่งที่ไวรัสอาจพยายามทำ | ป้องกันได้ไหม | เพราะอะไร |
|---|---|---|
| ดักแป้นพิมพ์ ขโมยรหัสตอนพิมพ์ | ❌ **ป้องกันที่ server ไม่ได้** | keylogger อยู่บนเครื่อง user เห็นก่อนข้อมูลออกจากเครื่อง → ต้องลงแอนตี้ไวรัสที่เครื่อง user + ไม่ใช้เครื่องสาธารณะ |
| ขโมย "ตั๋วเข้าระบบ" (cookie) ด้วยสคริปต์ | ✅ กันแล้ว | cookie ตั้ง **HttpOnly** → สคริปต์/JS อ่านไม่ได้ |
| เอา cookie ไปใช้ต่อจากเครื่องอื่น | 🟡 ลดความเสี่ยงแล้ว | cookie หมดอายุใน **8 ชม.** + ผูกกับ HTTPS — ช่วงที่ใช้ได้สั้นลงมาก (ถ้าต้องการเข้มกว่านี้ค่อยเพิ่มผูก IP/อุปกรณ์ภายหลัง) |
| หลอกให้ user เผลอกดส่งคำสั่ง (CSRF) | ✅ กันแล้ว | cookie ตั้ง **SameSite=Lax** |

---

## ถ้าโดนดักข้อมูลระหว่างทาง (user ↔ server)

| ภัย | ป้องกันได้ไหม | เพราะอะไร |
|---|---|---|
| ดักอ่านข้อมูล/รหัส ระหว่างเน็ต (sniffing) | ✅ กันแล้ว | ทุกอย่างวิ่งผ่าน **HTTPS เข้ารหัส** (Cloudflare) — คนกลางเห็นแต่ข้อมูลมั่ว |
| หลอกให้ลดเป็น http ธรรมดา (SSL strip) | ✅ กันแล้ว | header **HSTS** บังคับเบราว์เซอร์ใช้ HTTPS เท่านั้น |
| เอาหน้าเว็บเราไปฝังในเว็บปลอม (clickjacking) | ✅ กันแล้ว | header **X-Frame-Options: DENY** |
| หลอกชนิดไฟล์ (MIME sniffing) | ✅ กันแล้ว | header **X-Content-Type-Options: nosniff** |
| Reverse engineer ถอดโค้ดเรา | ✅ ความเสี่ยงต่ำ | แอปรันฝั่ง server (เครื่องเรา) — คนนอกเห็นแค่หน้า HTML ไม่เห็น logic |

## ฝั่ง server (กันคนเจาะเข้าเครื่อง)

ทำในรอบ red-team 2026-06-15 (ดู `MVP_SERVER_DEPLOY.md` หัวข้อ hardening):

- ปิด XAMPP (Apache/MySQL) ที่ไม่ได้ใช้ — ปิด 3 ประตูใหญ่
- SSH เข้าได้ด้วยกุญแจเท่านั้น (ปิดรหัสผ่าน) + เข้าได้แค่ผ่าน Tailscale
- เปิด Firewall ครบ + Windows Defender + UAC เปิดอยู่
- รหัสผ่านทุกคนเก็บแบบเข้ารหัส (hash) — ใครได้ DB ไปก็อ่านรหัสไม่ได้
- กันเดารหัสรัวๆ (ล็อก user + ล็อก IP)

---

## สิ่งที่โอควรทำ (ฝั่งคน ไม่ใช่ฝั่งโค้ด)

1. **เครื่องพนักงานที่ใช้เข้าระบบ** ควรมีแอนตี้ไวรัส (Windows Defender ก็พอ) และอัปเดต Windows — กัน keylogger ที่เรากันจาก server ไม่ได้
2. **อย่าใช้รหัสร่วมกัน** — แต่ละคนใช้ user ของตัวเอง (ระบบรองรับแล้ว) เวลาเกิดอะไรจะรู้ว่าใคร
3. **คนลาออก** → เข้าหน้า admin กด "ปิด" บัญชีเขาทันที
4. **อย่า login บนเครื่องสาธารณะ/เน็ตร้าน** ถ้าเลี่ยงได้

---

## ความเสี่ยงที่ยังเหลือ (พูดตรงๆ)

- **keylogger บนเครื่อง user** — แก้ที่ server ไม่ได้ ต้องดูแลเครื่อง user
- **session เก็บใน cookie (ไม่ใช่ฐานข้อมูล)** — เบาและเร็ว เหมาะ MVP; ถ้าอยากให้ admin "เตะ user ออกจากระบบทุกเครื่องทันที" ได้ ต้องเปลี่ยนเป็น server-side session (เพิ่มทีหลังได้ ถ้าจำนวนคน/ข้อมูลเงินมากขึ้น)
- ทั้งสองอย่างนี้เป็น trade-off ปกติของระบบขนาดนี้ ไม่ใช่ช่องโหว่จากความเลินเล่อ

## รอบตรวจที่ 2 (application logic, 2026-06-15)

ตรวจซ้ำมุมคนโจมตี คราวนี้ดู logic ในแอป เจอ + แก้แล้ว:

- **เมนูธุรกิจหลายตัวถูกล็อกเกินจำเป็น** (billing/rates/customers/fuel/dispatch ฯลฯ ไม่ได้อยู่ในตารางสิทธิ์ → ตกไปเป็น admin-only) → office/บัญชีใช้งานจริงไม่ได้ **แก้แล้ว** กำหนดสิทธิ์ตามงาน (import=admin เท่านั้น, email=admin+บัญชี, billing=office แก้ได้)
- **แอปคนขับ (PWA) ใช้ไม่ได้** เพราะระบบสิทธิ์ของออฟฟิศไปบล็อก → **แก้แล้ว** แยกระบบ auth คนขับ (PIN) ออกจากกัน คนขับเข้าได้ปกติ
- **ตรวจ IDOR (คนขับเห็นข้อมูลคนอื่น):** ปลอดภัย — ทุกหน้าคนขับดึงข้อมูลจาก session ของตัวเอง ไม่เชื่อ id ที่ส่งมาจากฝั่ง client → **คนขับเห็นเฉพาะของตัวเองจริง** (ตรงกับที่โอกังวล)
