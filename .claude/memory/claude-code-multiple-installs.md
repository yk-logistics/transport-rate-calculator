**Resolved 2026-06-08 — consolidated to a single npm-global install** at `C:\Users\guole\AppData\Roaming\npm\claude(.cmd)` (was 2.1.168). If `claude` ever runs a stale version again, this history explains why and what to check.

What was wrong: the machine had Claude Code in several places, and **different shells resolved `claude` to different installs**:
- `...\Python\Python312\Scripts\claude.bat` — a shim pointing to the native exe; it was FIRST on PATH so **cmd/PowerShell ran it → the stale native 2.1.153**. (Removed; backup `claude.bat.bak`.)
- `%LOCALAPPDATA%\Programs\claude.exe` + `~/.local/share/claude` — the **native install, stale 2.1.153**. (Removed.)
- `%APPDATA%\npm\claude(.cmd)` — **npm-global, current 2.1.168**. git-bash/the Bash tool resolved here, so `claude update` updated THIS one — but the user's PowerShell still ran the stale native via the shim. That mismatch is why it looked "updated" yet the user still saw the old version / Opus 4.7.
- The Claude **desktop app** ("ในนี้", entrypoint `claude-desktop`) bundles its OWN Claude Code and self-updates → it had Opus 4.8 first.

Why the model gap: the `/model` picker list ships baked into each CLI release (Opus 4.8 was added in 2.1.154). A stale terminal CLI shows older models than the auto-updating desktop app.

**How to apply:** if โอ says "updated but the version/model didn't change," the cause is almost always that the shell's `claude` resolves to a different install than the one that got updated. Check `where.exe claude` for the cmd/PowerShell order, and remember git-bash may resolve differently. It's now a single npm-global install so auto-update should keep it current; if a shim or a native reinstall reappears, remove it. See also [[feedback-qwen-and-subagent-cost]].

**`cc` shortcut (attempted then REMOVED 2026-06-09):** โอ likes typing `cc` to open Claude in Project YK. An early attempt wrote `C:\Users\guole\AppData\Roaming\npm\cc.cmd`, but that lives in the FS-divergent npm dir (see next note) so it never reached โอ's real terminal — **deleted**. With the native install now on PATH, โอ just types `claude`, or uses the Desktop shortcut. Any future `cc` shorthand must live where the tools can actually write to โอ's real disk (project/Desktop round-trip; `AppData\Roaming\npm` does NOT) and point to `%USERPROFILE%\.local\bin\claude.exe`. (FYI cmd has an AutoRun at `HKCU\...\Command Processor\AutoRun` that appends nodejs+npm to PATH, guarded by `_NPMPATH`.)

**FS-view divergence (found 2026-06-09 — STOP digging if this recurs):** spent ~8 rounds because โอ's real terminal/double-click reported `claude` / `claude.exe` NOT found, while the Claude Code **tool process** (Bash/PowerShell tools, medium integrity, same `home\guole` user, non-virtualized `C:\Users\guole\AppData\Roaming`) consistently SEES and runs `...\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe` (2.1.168). Same machine, same user, no symlinks/reparse points, npm ACL grants guole FullControl — yet `if exist` from โอ's Explorer-launched .bat returns missing. Conclusion: **the tool environment and โอ's real interactive shell do not see the same disk for `AppData\Roaming\npm`** (Desktop paths under `Project YK` DO reach โอ's real disk — โอ saw the .bat output — but the npm install does not round-trip). **Practical upshot:** you CANNOT fix โอ's native terminal CLI by editing `AppData\Roaming\npm` (cc.cmd, claude shims, the launcher .bat) through the tools — those writes don't land where โอ's terminal reads. A working native terminal CLI needs a **clean native install run in โอ's OWN real terminal**. For daily use this is moot — the **Code tab is the working Claude Code**. Don't re-investigate the mechanism; just recommend the Code tab or a native reinstall. **Root cause CONFIRMED 2026-06-09:** the Claude Desktop app is a **packaged MSIX app** — found `C:\Users\guole\AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\npm\claude.cmd`. Its `%APPDATA%\Roaming` is transparently virtualized to `Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming`, so tools running inside the app read/write a PRIVATE virtual AppData while โอ's real Explorer/terminal use the real `C:\Users\guole\AppData\Roaming`. `$env:APPDATA` still prints the normal path (virtualization is invisible to the app), which is why every check "looked" same-machine. `Desktop`/`Project YK` paths are NOT virtualized → writes there DO reach โอ's real disk.

**RESOLVED 2026-06-09 — native install fixed โอ's real terminal.** The broken npm-global path was abandoned. Ran the official native installer in โอ's OWN real PowerShell: `irm https://claude.ai/install.ps1 | iex`. It installed **`C:\Users\guole\.local\bin\claude.exe` (2.1.169)** — confirmed working via full-path `--version`. Installer did NOT add `~/.local/bin` to PATH, so bare `claude` failed until we appended it to the **User** PATH (PowerShell `[Environment]::SetEnvironmentVariable("Path", ...+";"+"$env:USERPROFILE\.local\bin", "User")`). Two non-obvious things: (1) PATH edits must be done in โอ's real shell, not via the tools (FS/registry divergence). (2) **Launchers for โอ must point to `%USERPROFILE%\.local\bin\claude.exe` and live under the project/Desktop** (those DO round-trip to โอ's real disk; `AppData\Roaming\npm` does NOT). The Desktop shortcut **"Claude (Project YK)"** → `_Claude Tools\start_claude_projectYK.bat` now `cd`s into the project and runs the native claude — one-click open in the right folder. Reminder for โอ: Claude Code operates on the folder it's started in, so always launch from the project dir (the shortcut handles this), never from `system32`.

**Primary surface:** โอ works mainly in the **Claude Desktop app → Code tab** (already Opus 4.8 by default), NOT the terminal. The Code tab is the same Claude Code (same tools, subagents, Qwen delegation all work from there) and is the better fit for a non-coder. Terminal-CLI launchers/shortcuts (e.g. `_Claude Tools/start_claude_projectYK.bat` + the desktop `.lnk`) are optional — don't push terminal workflows on โอ.
